## 勘查为什么必要

1. 仲裁模块要挂到每个轴的对象上，因此必须先确认 `Axis_t` 里已有的事件组、状态机、位置和状态字段，避免重复建一套轴模型。
2. 设计要求 `rt_mq + 每轴 rt_mutex + 独立仲裁线程`。当前代码只有 `rt_event`，没有实际使用 `rt_mq` 或 `rt_mutex`，但 rtconfig 已经开启全部所需组件，可以直接实施。
3. 每增加线程都会消耗栈和优先级；`Task\task_stack.h` 是当前栈大小的集中登记点，新仲裁线程必须同步加入该表。
4. `Dev_Registry_Add` 已经具备“注册时创建 C 模式线程”的路径，这会影响仲裁线程的启动位置和初始化时序，必须先看清现状再接线。
5. 极性、限位和系统状态已经会向轴事件组或系统事件组发事件；仲裁模块的消费点和事件语义需要与这些现有发送点对齐。

```c
    case POLARITY_UNPOWERED: Act_Event_Send(EVT_ACT_POWER_LOST);     break;
    case POLARITY_FWD:       Act_Event_Send(EVT_ACT_POLARITY_FWD);   break;
    case POLARITY_REV:       Act_Event_Send(EVT_ACT_POLARITY_REV);   break;
    case POLARITY_ABNORMAL:  Act_Event_Send(EVT_ACT_POWER_ABNORMAL); break;
    default: break;
    }
}
```

调用位置是 `Task\di_task.c:15-18`，实际周期为 `DI_SCAN_PERIOD_MS=2ms`（`di_task.h:12`）；5 点窗口合计 10ms 消抖。极性跳变打印被延迟到 `Polarity_PrintPending()`，由 main 1s 循环调用（`main.c:76`）。

## 额外实施风险

1. **轴事件没有消费者**：`evt_act` 只有创建和发送，没有接收线程。仲裁线程必须补上这个消费端。
2. **`Axis_t.dir` 全部是 `ACT_DIR_NONE`**：`App_Model_Init` 没有配置有效轴，所以 `sys_enter_run` 里的轴使能循环不会发任何 `EVT_ACT_WORK_ENABLE`。仲裁接线前需要确定轴配置来源。
3. **无消息队列/互斥量使用**：组件已开启，但业务代码还没有现成 `rt_mq`/`rt_mutex` 模式可复制；仲裁模块是新引入的第一处。
4. **注册时立即 init 的时序**：当前 `main` 在 `App_Model_Init` 前注册设备；依赖轴事件组的模块不能把“注册即 init”当作最终初始化时机。
5. **`Sys_State_Dispatch` 有疑似括号错误**：`dev_state.c:81-93` 中 `EVT_SYS_OVER_CURRENT` 分支缺少一个闭合大括号，导致 `EVT_SYS_ROD_LIMIT_FAULT` 分支在文本作用域上位于过流分支内部。虽然当前按 C 语义是“过流发生时才检查推杆故障”，但这大概率不是业务意图，实施仲裁前建议单独确认和修复。
6. **栈登记表与实际线程集合可能不同**：`Task_Stack_Dump` 登记了 timer，但当前 `rtconfig.h` 未开 soft timer；新增仲裁线程后要同时更新 `s_task_stack[]`，避免水位监控漏登记。
